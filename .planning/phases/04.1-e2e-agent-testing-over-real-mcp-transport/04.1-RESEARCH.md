## Summary

This phase delivers two production changes and one opt-in test. The research confirms all
critical decisions from CONTEXT.md are technically sound and provides concrete
implementation patterns.

**D-07 resolution (the most important unknown):** `claude -p --mcp-config` DOES support
per-server HTTP `headers` in the JSON config, using the exact schema the CONTEXT.md
proposes. Verified by running `claude mcp add --transport http --header` on Claude Code
v2.1.160 and inspecting the written `~/.claude.json` entry. The key name is `"type":
"http"` (not `"transport"`), and `"headers"` is a flat string-to-string object at the
same level as `"url"`. This is the PRIMARY credential path for the test.

**`/healthz` carve-out approach:** `@mcp.custom_route("/healthz", methods=["GET"])` is
available in FastMCP 3.3.1 and is documented as bypassing FastMCP's own auth middleware.
However, the project's `CredentialMiddleware` is a separate pure-ASGI class that wraps
the entire Starlette app. Because `CredentialMiddleware` is applied as Starlette
middleware (outermost wrapper), it intercepts `/healthz` before the route is reached.
The correct fix is a **path-based short-circuit inside `CredentialMiddleware.__call__`**,
checking `scope["path"] == "/healthz"` after the `type == "http"` guard and passing
through without credential validation. The `@mcp.custom_route` decorator is still used
to register the handler — but the middleware path-check is what makes it accessible.

**`claude -p` invocation:** Confirmed flags for headless non-interactive MCP use:
`--print`, `--mcp-config <file>`, `--strict-mcp-config`, `--allowedTools "mcp__godoo__*"`,
`--output-format json`. The `--permission-mode bypassPermissions` flag is available but
overly broad; prefer `--allowedTools "mcp__godoo__*"` which pre-approves exactly the
MCP server's tools without bypassing all other safety checks. For the test, we only
need the godoo MCP tools, so `mcp__godoo__*` wildcard is the right choice.

**Primary recommendation:** Implement the three code changes (HOST/PORT env,
`/healthz` with middleware carve-out, `e2e` marker in pyproject.toml) as Wave 0, then
build the `tests/e2e/` harness using subprocess + httpx polling + `claude -p` invocation.

### Pattern 1: Ephemeral Port Allocation

**What:** Bind a temporary socket to `("127.0.0.1", 0)` to let the OS assign a free port. Read the assigned port, close the socket, then pass the port to the subprocess via env var.

**Why this over alternatives:** Binding on port 0 then checking `getsockname()[1]` is the canonical POSIX/Windows pattern. There is a TOCTOU window between socket close and subprocess bind, but it's negligible on loopback at test time. Do NOT pass `PORT=0` to uvicorn and then discover the port from its output — parsing stdout is fragile.

```python
# Source: canonical Python socket stdlib
import socket

def _find_free_port() -> int:
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
        sock.bind(("127.0.0.1", 0))
        return sock.getsockname()[1]
```
[VERIFIED: Python stdlib socket docs — `bind(("host", 0))` pattern is standard]

### Pattern 2: Subprocess Server Launch and Teardown

**What:** Launch `python -m godoo_mcp_server` as a subprocess via `asyncio.create_subprocess_exec`, poll `/healthz`, yield to tests, then terminate.

**When to use:** Only in `tests/e2e/conftest.py` — not in integration tests which use `ASGITransport`.

```python
# Source: asyncio.subprocess stdlib + httpx for polling
import asyncio
import socket
import sys
import os
import httpx
import pytest_asyncio

@pytest_asyncio.fixture(scope="session", loop_scope="session")
async def server_process(odoo_harness):
    """Launch godoo-mcp-server on an ephemeral loopback port. Polls /healthz."""
    port = _find_free_port()
    proc = await asyncio.create_subprocess_exec(
        sys.executable, "-m", "godoo_mcp_server",
        env={
            **os.environ,
            "HOST": "127.0.0.1",
            "PORT": str(port),
        },
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )
    base_url = f"http://127.0.0.1:{port}"
    # Poll /healthz — no credentials needed
    async with httpx.AsyncClient() as client:
        deadline = asyncio.get_event_loop().time() + 30.0
        while True:
            try:
                r = await client.get(f"{base_url}/healthz", timeout=2.0)
                if r.status_code == 200:
                    break
            except (httpx.ConnectError, httpx.TimeoutException):
                pass
            if asyncio.get_event_loop().time() > deadline:
                proc.terminate()
                raise RuntimeError(f"Server did not start within 30s on port {port}")
            await asyncio.sleep(0.2)
    try:
        yield base_url
    finally:
        proc.terminate()
        try:
            await asyncio.wait_for(proc.wait(), timeout=10.0)
        except asyncio.TimeoutError:
            proc.kill()
```
[ASSUMED — pattern inferred from asyncio.subprocess stdlib; actual timeout values should be adjusted based on real startup time]

### Pattern 3: `claude -p` Headless Invocation

**What:** Run `claude -p <prompt> --mcp-config <file> --strict-mcp-config --allowedTools "mcp__godoo__*" --output-format json`

**Why `--strict-mcp-config`:** Prevents the test from accidentally loading the developer's own MCP config — ensures only the godoo server is available.

**Why `--allowedTools "mcp__godoo__*"`:** Pre-approves all tools from the `godoo` MCP server without bypassing other permission checks. Does NOT require `--dangerously-skip-permissions` or `bypassPermissions`.

```python
# Source: Claude Code v2.1.160 --help output [VERIFIED]
import asyncio
import json

async def run_agent(prompt: str, mcp_config_path: str, timeout: float = 120.0) -> dict:
    proc = await asyncio.create_subprocess_exec(
        "claude", "-p", prompt,
        "--mcp-config", mcp_config_path,
        "--strict-mcp-config",
        "--allowedTools", "mcp__godoo__*",
        "--output-format", "json",
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )
    try:
        stdout, stderr = await asyncio.wait_for(proc.communicate(), timeout=timeout)
    except asyncio.TimeoutError:
        proc.kill()
        raise
    return json.loads(stdout.decode())
```
[VERIFIED: flag names confirmed from `claude --help` on v2.1.160 installed locally]

### Pattern 4: MCP Config JSON Schema

**Definitive schema** (confirmed by adding a real server with `claude mcp add --transport http --header` and inspecting `~/.claude.json`):

```json
{
  "mcpServers": {
    "godoo": {
      "type": "http",
      "url": "http://127.0.0.1:{port}/mcp",
      "headers": {
        "X-Odoo-Url": "http://odoo-container:8069",
        "X-Odoo-Database": "test_odoo",
        "X-Odoo-Username": "admin",
        "X-Odoo-Password": "admin"
      }
    }
  }
}
```

Key schema facts:
- Top-level key is `"mcpServers"` (camelCase)
- Server entry uses `"type": "http"` (NOT `"transport"`)
- `"headers"` is a flat `{string: string}` object at the same level as `"url"`
- `"url"` should point to the `/mcp` path — this is the MCP endpoint, not the server root

[VERIFIED: inspected `~/.claude.json` after `claude mcp add --transport http --header "X-Test: value" --scope local godoo-test http://127.0.0.1:9999/mcp` on Claude Code v2.1.160]

### Pattern 5: `/healthz` Carve-Out in `CredentialMiddleware`

**The problem:** `CredentialMiddleware` is passed as Starlette `Middleware` to `mcp.http_app()`. In `create_streamable_http_app`, `create_base_app` wraps the entire Starlette router with middleware. Therefore `CredentialMiddleware.__call__` is invoked for EVERY HTTP request, including requests to routes registered via `@mcp.custom_route("/healthz")`. The `@mcp.custom_route` decorator's "no auth" property only applies to FastMCP's own `RequireAuthMiddleware` — not to `CredentialMiddleware`.

**The correct fix:** Path-based short-circuit inside `CredentialMiddleware.__call__`, after the `type == "http"` guard:

```python
# src/godoo_mcp_server/credentials.py — modification to CredentialMiddleware.__call__
async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
    if scope["type"] != "http":
        await self._app(scope, receive, send)
        return

    # Carve out /healthz — unauthenticated, no credentials required.
    # This is also used as Docker HEALTHCHECK in Phase 5.
    if scope.get("path") == "/healthz":
        await self._app(scope, receive, send)
        return

    # ... rest of credential extraction unchanged ...
```

**The route handler** is registered separately in `server.py` using the FastMCP decorator:

```python
# src/godoo_mcp_server/server.py — add after mcp instance creation
from starlette.requests import Request
from starlette.responses import JSONResponse

@mcp.custom_route("/healthz", methods=["GET"])
async def healthz(request: Request) -> JSONResponse:
    return JSONResponse({"status": "ok"})
```

**Why this is the right split:**
- Middleware short-circuit: minimal change, no new imports, preserves the pure-ASGI design constraint.
- Handler registration: `@mcp.custom_route` is the FastMCP-idiomatic way to add routes; it populates `mcp._additional_http_routes` which is included by `create_streamable_http_app`.
- Both changes together: middleware passes `/healthz` through; router delivers it to the handler.

[VERIFIED: FastMCP 3.3.1 `create_streamable_http_app` source inspected — `server._get_additional_http_routes()` is called inside the function and routes are added to the Starlette router; Starlette middleware wraps all routes]

### Pattern 6: `--output-format json` Result Shape

When `claude -p --output-format json` exits, stdout is a single JSON object:

```json
{
  "type": "result",
  "subtype": "success",
  "result": "I have created the partner category...",
  "is_error": false,
  "session_id": "abc-123",
  "total_cost_usd": 0.0034,
  "duration_ms": 4200,
  "duration_api_ms": 2100,
  "num_turns": 3
}
```

For error cases, `"is_error": true` and `"subtype"` may be a failure code such as
`"error_max_structured_output_retries"` (only when `--json-schema` is used) or reflect
an authentication failure.

**Assertion strategy for the test:**
1. Check `result["is_error"] == False`
2. Check `result["subtype"] == "success"`
3. Independently verify via `odoo_harness.client.search_read(...)` — do NOT rely solely on `result["result"]` text content.

[CITED: https://code.claude.com/docs/en/agent-sdk/structured-outputs — result shape confirmed from SDK docs and WebSearch cross-verification]

### Anti-Patterns to Avoid

- **Do NOT use `--permission-mode bypassPermissions`** — it bypasses ALL safety checks, not just MCP tool prompts. Use `--allowedTools "mcp__godoo__*"` instead. [VERIFIED: permissions docs at code.claude.com]
- **Do NOT use `--dangerously-skip-permissions`** — it permanently bypasses all prompts including filesystem writes. Wrong tool for an MCP-only test.
- **Do NOT inject Odoo credentials into the server subprocess env** — D-07 is to exercise the header path; the test must use headers via `--mcp-config`.
- **Do NOT assert only on the agent's `result` text field** — D-02 requires independent Odoo verify-back via `odoo_harness.client`.
- **Do NOT poll `/mcp` for readiness** — it requires credentials and returns 401 without them. Use `/healthz` (unauthenticated 200).
- **Do NOT use `ASGITransport` in e2e tests** — the point of this phase is to exercise the real TCP transport. The in-process pattern exists in `tests/integration/`; the new `tests/e2e/` must use a real socket.
- **Do NOT place fixtures in `tests/integration/conftest.py`** — the e2e fixtures live in `tests/e2e/conftest.py`. The `odoo_harness` fixture from `tests/integration/conftest.py` can be reused IF pytest can discover it across dirs (verify with `conftest.py` placement or re-export in `tests/e2e/conftest.py`).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Ephemeral port finding | Custom retry loop scanning ports | `socket.bind(("127.0.0.1", 0))` | OS guarantees uniqueness; no collision possible |
| Auth bypass for /healthz | Custom auth token or header skip logic | Path short-circuit in `CredentialMiddleware` | Minimal change; no new attack surface |
| HTTP readiness polling | TCP connect-only probe | `httpx.AsyncClient.get("/healthz")` | HTTP 200 confirms the ASGI server is serving, not just accepting connections |
| MCP config format | Hand-written JSON string | Confirmed schema from live `claude mcp add` output | Wrong key names cause silent failure (server ignored) |
| Agent output parsing | Text-based parsing of stdout | `json.loads(stdout)` on the `--output-format json` result | Text output is free-form; JSON result is structured and stable |

## Common Pitfalls

### Pitfall 1: Wrong `"type"` key in MCP config

**What goes wrong:** Using `"transport": "http"` instead of `"type": "http"` in the mcpServers JSON — the server is silently ignored by the claude CLI.

**Why it happens:** The `claude mcp add --transport http` CLI flag name uses "transport" but the JSON schema uses "type". Confusion between CLI arg and config key.

**How to avoid:** Always use the schema verified from live inspection: `"type": "http"`. Write the config file with a helper function that uses the verified schema constants.

**Warning signs:** Agent subprocess exits with an error or produces no MCP tool calls — claude falls through to its default tools with no godoo MCP server available.

[VERIFIED: confirmed by inspecting `~/.claude.json` after `claude mcp add --transport http`]

### Pitfall 2: `CredentialMiddleware` intercepts `/healthz` before route is reached

**What goes wrong:** Adding `@mcp.custom_route("/healthz")` without modifying `CredentialMiddleware` causes `/healthz` to return 401 during readiness polling, causing the fixture to time out.

**Why it happens:** Starlette middleware wraps the ENTIRE router. Even though `@mcp.custom_route` is documented as "bypassing auth," this refers only to FastMCP's own `RequireAuthMiddleware` — not to user-provided middleware like `CredentialMiddleware`.

**How to avoid:** Add the path short-circuit in `CredentialMiddleware.__call__` before running credential extraction (see Pattern 5 above).

**Warning signs:** The `server_process` fixture times out waiting for `/healthz` to return 200; manual `curl http://127.0.0.1:{port}/healthz` returns 401.

### Pitfall 3: `odoo_harness` fixture scope/conftest visibility

**What goes wrong:** `tests/e2e/conftest.py` defines `server_process` as a fixture depending on `odoo_harness`, but pytest cannot find `odoo_harness` because it lives in `tests/integration/conftest.py` (not a parent directory).

**Why it happens:** pytest fixture lookup climbs parent `conftest.py` files, not sibling directories. `tests/integration/` and `tests/e2e/` are siblings, so fixtures in `tests/integration/conftest.py` are not automatically visible to `tests/e2e/`.

**How to avoid:** Either (a) move `odoo_harness` to `tests/conftest.py` (root-level, visible to all), or (b) re-import and re-export it in `tests/e2e/conftest.py`. Option (a) is cleaner but may affect whether integration tests still run when Docker is absent. Option (b) is safer: import in e2e conftest with `from tests.integration.conftest import odoo_harness as odoo_harness`.

**Warning signs:** `pytest tests/e2e/ -m e2e` fails with "fixture 'odoo_harness' not found."

### Pitfall 4: Agent receives no task prompt about the correct model

**What goes wrong:** The agent creates a `res.partner` record instead of `res.partner.category`, or names the record differently than expected, causing the verify-back search to find nothing.

**Why it happens:** LLMs are non-deterministic. A vague prompt yields inconsistent model/field choices.

**How to avoid:** Make the prompt VERY specific: include the exact model name (`res.partner.category`), exact field (`name`), and an exact value (use a UUID-tagged name like `E2ETest-<uuid4[:8]>`). Verify-back searches for that exact value.

**Warning signs:** `odoo_harness.client.search_read(...)` returns empty list even when the agent claimed success.

### Pitfall 5: `--strict-mcp-config` absent — developer's MCP config leaks into test

**What goes wrong:** Without `--strict-mcp-config`, Claude loads its user-level and project-level MCP configs alongside the test config. The agent may call tools from unrelated servers.

**Why it happens:** `--mcp-config` ADDS servers to the session; it does not replace all servers.

**How to avoid:** Always pass `--strict-mcp-config` alongside `--mcp-config` in the test invocation.

**Warning signs:** Agent calls tools from other MCP servers not in the test config; test becomes environment-dependent.

### Pitfall 6: `loop_scope` mismatch for session-scoped async fixtures

**What goes wrong:** `server_process` is a session-scoped async fixture but is decorated `@pytest_asyncio.fixture(scope="session")` without `loop_scope="session"` — the fixture runs in a different event loop than the test that depends on it.

**Why it happens:** `pytest-asyncio` 1.x requires explicit `loop_scope="session"` on session-scoped async fixtures (matching the pattern in `tests/integration/conftest.py`).

**How to avoid:** Decorate all session-scoped async fixtures as:
```python
@pytest_asyncio.fixture(scope="session", loop_scope="session")
async def server_process(...):
```

**Warning signs:** RuntimeError about event loop being closed, or "ScopeMismatch: You tried to access the function scoped fixture ... with a session-scoped request object."

### Agent-driven write test

```python
# tests/e2e/test_agent_write_flow.py
import asyncio, json, uuid
import pytest
from pathlib import Path
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from godoo.testcontainers import StartedOdooContainer

@pytest.mark.e2e
@pytest.mark.asyncio(loop_scope="session")
async def test_agent_creates_partner_category(
    mcp_config_file: Path,
    odoo_harness: "StartedOdooContainer",
) -> None:
    """D-02: agent creates res.partner.category; Odoo verify-back confirms the record exists."""
    tag_name = f"E2ETest-{uuid.uuid4().hex[:8]}"
    prompt = (
        f"Using the godoo MCP tools, create a partner category (res.partner.category) "
        f"with the name '{tag_name}'. Return the id of the created record."
    )
    proc = await asyncio.create_subprocess_exec(
        "claude", "-p", prompt,
        "--mcp-config", str(mcp_config_file),
        "--strict-mcp-config",
        "--allowedTools", "mcp__godoo__*",
        "--output-format", "json",
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )
    try:
        stdout, stderr = await asyncio.wait_for(proc.communicate(), timeout=120.0)
    except asyncio.TimeoutError:
        proc.kill()
        pytest.fail("Agent subprocess timed out after 120s")

    result = json.loads(stdout.decode())

    # D-02: assert on agent's JSON result first
    assert result.get("is_error") is False, (
        f"Agent returned is_error=True. stderr={stderr.decode()!r}"
    )
    assert result.get("subtype") == "success", (
        f"Agent subtype not 'success': {result.get('subtype')!r}"
    )

    # D-02: independent Odoo verify-back — never trust the agent's claim alone
    records = await odoo_harness.client.search_read(
        "res.partner.category",
        domain=[["name", "=", tag_name]],
        fields=["id", "name"],
    )
    assert len(records) == 1, (
        f"Expected 1 partner category with name={tag_name!r}, found {len(records)}. "
        f"Agent result: {result.get('result', '')!r}"
    )
```

## Open Questions

1. **`odoo_harness` conftest visibility across `tests/integration/` → `tests/e2e/`**
   - What we know: pytest discovers conftest.py by climbing the directory tree from the test file. `tests/integration/conftest.py` is not in the parent chain of `tests/e2e/`.
   - What's unclear: Is it better to (a) move `odoo_harness` to `tests/conftest.py`, or (b) re-export from `tests/e2e/conftest.py`?
   - Recommendation: Move `odoo_harness` and `second_user_credentials` to `tests/conftest.py`. The session-scoped Docker fixture is shared infrastructure; it belongs at the root level. The e2e phase is a good time to make this structural improvement. (Verify: do existing integration tests break if conftest.py at their level no longer defines `odoo_harness`? They inherit from parent — should be fine.)

2. **`sys.executable` vs. `uv run` for subprocess server launch**
   - What we know: `uv run pytest` runs tests with the venv Python, so `sys.executable` points to the venv Python. `python -m godoo_mcp_server` with `sys.executable` should work.
   - What's unclear: Does this hold when running on CI (if it's ever added) or with different `uv` invocations?
   - Recommendation: Use `sys.executable, "-m", "godoo_mcp_server"` — this is the most portable pattern. Document the assumption in a comment.

3. **`server_process` fixture scope: session vs. function**
   - What we know: Session-scoped avoids the ~5s uvicorn startup cost per test. Function-scoped provides cleaner isolation.
   - What's unclear: We have only one e2e test, so it doesn't matter yet.
   - Recommendation: Session-scoped (mirrors `odoo_harness`). Matches the design seed's intent. Cheap to change later.
