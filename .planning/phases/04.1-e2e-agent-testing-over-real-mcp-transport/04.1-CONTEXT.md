# Phase 04.1: E2E agent testing over real MCP transport - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver a true end-to-end test in which a **headless `claude -p` agent** drives the
godoo MCP tools over a **real Streamable-HTTP transport on an actual TCP socket** against
a **subprocess-launched** server, performing **one agent-driven WRITE** whose side-effect
is then **independently verified in Odoo** through the same test harness.

This closes the gap left by Phase 4, where every integration test talks to the server
in-process via `httpx.ASGITransport(app=...)` and nothing exercises the real transport,
the `CredentialMiddleware` path as a real client hits it, or an agent's own tool-selection
behavior against the live `/mcp` endpoint.

**In scope:** the enabling production change (HOST/PORT env support + a `/healthz` route),
one opt-in `@pytest.mark.e2e` write-flow test, the subprocess + MCP-config fixtures, and
local run docs.

**Out of scope (deferred):** CI integration / `ANTHROPIC_API_KEY` CI job (local-first per
maintainer); broad multi-flow matrix; Code-Mode (`execute_odoo_code`) e2e — Code Mode is
Phase 6.

</domain>

<decisions>
## Implementation Decisions

### Harness & placement (locked by design seed)
- **D-01:** MCP client = **headless `claude -p`** (Claude Code), spawned as a subprocess
  from a pytest test.
- **D-02:** First e2e test = **ONE agent-driven WRITE flow, verified in Odoo** — assert on
  BOTH the agent's JSON result AND the independent Odoo side-effect (read the record back
  through the harness), never the agent's claim of success alone.
- **D-03:** **Opt-in / local-first.** New `@pytest.mark.e2e` marker, **default-deselected**
  (mirrors the existing `integration` marker). Must **skip cleanly (not error)** when
  Docker, the `claude` CLI, or Claude auth is absent.
- **D-04:** Placement = decimal **Phase 4.1, before Phase 5 (Package & Ship)** — E2E proof
  before shipping.

### Server enabling changes
- **D-05:** Add **`HOST` / `PORT` env-var support** to `src/godoo_mcp_server/__main__.py`
  (conventional names, NOT `GODOO_MCP_*`), defaulting to `0.0.0.0` / `8000`. Current code
  hardcodes `0.0.0.0:8000` at `__main__.py:20`. This lets the harness bind an ephemeral port.
- **D-06:** **Add a lightweight `/healthz` route, carved OUT of `CredentialMiddleware`.**
  Rationale: `CredentialMiddleware` wraps the whole ASGI app, so a health probe that sends
  no credentials would otherwise return 401. `/healthz` must be reachable WITHOUT credentials
  and return 200 once the server is accepting connections. This route is also reusable as a
  Docker `HEALTHCHECK` in Phase 5. (Chosen over polling `/mcp` — which is credential-gated and
  returns ambiguous 401/406 — and over a full MCP `initialize` handshake, which is overkill for v1.)

### Credential model for the test
- **D-07:** **Use the `X-Odoo-*` header path**, NOT `ODOO_*` env-var injection. The temp MCP
  client config points the agent at the server with per-server HTTP headers carrying the Odoo
  credentials:
  ```json
  {"mcpServers": {"godoo": {"type": "http", "url": "http://127.0.0.1:{port}/mcp",
    "headers": {"X-Odoo-Url": "...", "X-Odoo-Database": "...",
                "X-Odoo-Username": "...", "X-Odoo-Password": "..."}}}}
  ```
  **Why this over the seed's env-var lean:** it exercises the same per-user header-injection
  path that `godoo-proxy` (the commercial gateway) uses in production — the highest-value path
  to cover end-to-end. `CredentialMiddleware` already supports headers with **headers > env**
  precedence (`credentials.py:74-77`).
  - **RESEARCH FLAG:** confirm the current `claude` CLI `--mcp-config` schema supports per-server
    custom HTTP `headers` for an `http`-type server. If it does NOT, fall back to `ODOO_*` env-var
    injection into the subprocess (the seed's v1 default) and note the gap.
  - The credentials written into the temp config are the **throwaway testcontainers admin
    password (`admin`)**, not a real secret. Write the config into a pytest `tmp_path` and let it
    be cleaned up with the temp dir.

### Skip-guard / prerequisite detection
- **D-08:** Detect prerequisites cheaply, **no billable Claude call:**
  - `claude` CLI: `shutil.which("claude")` present AND `claude --version` exits 0.
  - Docker: rely on the **existing `godoo-testcontainers` harness** — if Docker is unavailable
    the session Odoo fixture fails/skips naturally (same as integration tests).
  - Auth: **best-effort.** Do not pre-probe auth. If the agent subprocess fails with an
    auth-specific signal at runtime, surface it as a clean skip with a clear message rather
    than a hard error where feasible.

### Write-flow target & cleanup
- **D-09:** First write target = **`res.partner.category`** (matches the existing vertical
  test; minimal fields — just `name`; easy verify-back via a `record_search` on the name).
- **D-10:** **Ephemeral container, no explicit record cleanup** — the session-scoped
  testcontainers Odoo is throwaway; teardown happens at session end. Verify-back is by
  searching for the created category name, mirroring the delete-then-search verification
  pattern in `test_vertical.py`.

### Test runner & docs
- **D-11:** Document the local run command (likely `uv run pytest -m e2e`) and prerequisites
  (Docker, `claude` on PATH, Claude auth, cost note) in README / dev notes. Each e2e run makes
  a real **billable** Claude call — keep the suite tiny and tightly scoped to one deterministic write.

### Claude's Discretion
- Exact `claude -p` invocation flags for non-interactive permission handling (e.g.
  `--allowedTools "mcp__godoo__*"`, `--output-format json`, and any permission-mode / bypass
  flag) — verify against current Claude Code CLI docs at plan/research time.
- Ephemeral-port allocation mechanism, readiness retry/backoff timing, and per-test timeout
  values (set generous — the agent call is non-deterministic and network/LLM-bound).
- Exact shape of the `/healthz` response body and how the route is registered relative to the
  fastmcp `http_app` mount + `CredentialMiddleware`.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`odoo_harness` (session-scoped) in `tests/integration/conftest.py`** — reuse directly to
  get a real Odoo 17 with `.url` / `._database` / admin password `admin`. The new e2e
  fixtures layer a server subprocess on top of this.
- **`CredentialMiddleware` header path** — already supports `X-Odoo-*` headers (D-07); no
  middleware change needed for credentials, only the `/healthz` carve-out (D-06).
- **`test_vertical.py` assertion idiom** — JSON-parse `result["content"][0]["text"]`, check a
  domain key, then re-query to confirm the side-effect. Reuse for the verify-back step.

### Established Patterns
- **Opt-in marker + default-deselect** — `integration` marker is deselected via
  `addopts = -m 'not integration'`. The `e2e` marker follows the same pattern (D-03); the
  default-deselect expression must be updated to also exclude `e2e`.
- **Pure-ASGI middleware** — `CredentialMiddleware` is raw ASGI (not Starlette
  `BaseHTTPMiddleware`) to avoid contextvar issues with the MCP SDK; the `/healthz` route must
  fit this composition (carved out before/around the credential check).

### Integration Points
- **New `tests/e2e/` package** — `conftest.py` (server-subprocess fixture + temp MCP-config
  fixture, reusing `odoo_harness`) and `test_agent_write_flow.py` (the single write test).
- **`__main__.py`** — HOST/PORT env reading is the seam that lets the fixture bind an
  ephemeral 127.0.0.1 port.
- **`server.py`** — `/healthz` route registration is the seam for readiness probing + Phase 5
  Docker HEALTHCHECK.

</code_context>

<specifics>
## Specific Ideas

- Bind the subprocess to `127.0.0.1` (loopback) on an ephemeral port — not `0.0.0.0` — for the test.
- Keep the agent task prompt tightly scoped to one deterministic create so the assertion is stable.
- Readiness: poll `/healthz` (unauthenticated, 200) in a retry loop with a timeout before launching the agent.
- Verify-back: search `res.partner.category` for the created name and assert the record exists, in addition to parsing the agent's JSON result.

</specifics>
